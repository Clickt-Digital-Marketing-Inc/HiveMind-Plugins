# Canonical project root structure

The coordinator structures every project root the same way, so any Claude session lands in a familiar layout and knows where to look.

```
<project-root>/
├── CLAUDE.md            # Governance — generated by plan-to-linear-build, never by hand
├── docs/
│   ├── PROJECT.md       # Project home doc — generated from assets/PROJECT.template.md
│   └── <idea-name>.md   # The project brief delivered by idea-refinement
└── tasks/
    └── todo.md          # Local scratchpad: plan for the CURRENT issue as checkable items
```

Lessons are NOT a local file — they live in the project's Linear document **"Lessons Log"** (created by `plan-to-linear-build`, appended after any correction, read at every session start).

## What each file is for

- **`CLAUDE.md`** — enforces the discipline every session: Linear-issue-as-prompt workflow with boundary sync (plan comment on start, wrap-up comment on completion), plan mode + verification gates, `/reflexion:reflect` at the end of every issue on software projects, integration checks at milestone boundaries, and the Lessons Log loop. It is produced and customized by `plan-to-linear-build` from its template. The coordinator only verifies it exists and that no `{{PLACEHOLDER}}` is left unfilled — it never writes a competing version.
- **`docs/PROJECT.md`** — the stable home doc: summary, domain, tools & channels, Linear team/project link, milestone list, pointer to the brief. This is orientation, not tracking.
- **`docs/` working files** — non-code projects keep drafts, copy decks, and asset lists under `docs/` (a `docs/drafts/` subfolder is fine as volume grows). Finished artifacts live where the domain publishes them (CMS, scheduler, signed contracts folder); Linear issues name those locations.
- **`docs/<idea-name>.md`** — the brief exactly as `idea-refinement` delivered it (kebab-case filename). If the brief was written elsewhere (e.g. the root), propose moving it here and do so with the user's OK — keep their filename if they prefer it. Do not edit its content while moving it.
- **`tasks/todo.md`** — local scratchpad for the issue currently being executed: the plan as checkable items, marked off as work proceeds. The Linear comments (plan on start, wrap-up on completion) are the record; this file is working state. Reset per issue.

## What does NOT go in files

- **Work tracking.** Issues, their status, and their acceptance criteria live in Linear only. `tasks/todo.md` is a per-issue execution scratchpad, not a backlog. If it starts accumulating future work, that work becomes Linear issues.
- **Decisions made after planning.** A decision that changes scope or architecture gets reflected in the affected Linear issues (via the grooming loop, with approval), not buried in a doc.
- **Lessons.** No local lessons file — the Linear "Lessons Log" document is the single canonical store. A `tasks/lessons.md` found in the repo is drift: propose migrating its entries into the Lessons Log.
- **Duplicate status.** Never maintain a progress table in `PROJECT.md` or `README` — it will drift from Linear, and Linear wins.

## Creation rules

- Create directories and files only if missing. If a file already exists, read it, show the user what you would add or move, and merge with their approval — never overwrite silently.
- Fill `PROJECT.md` with what is known at creation time; leave Linear-dependent fields (`{{LINEAR_PROJECT_URL}}`, `{{MILESTONE_LIST}}`) as placeholders only until `plan-to-linear-build` completes — the coordinator backfills them in pipeline step 4 of the same session.
- If the project folder or repo has its own conventions (existing `docs/` layout, a `CONTRIBUTING.md`, a shared-drive structure), adapt to it rather than forcing this layout — the required invariants are: brief findable under `docs/`, `tasks/todo.md` present (CLAUDE.md uses it as the local plan scratchpad), root `CLAUDE.md` present.
